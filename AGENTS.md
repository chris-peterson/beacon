# beacon

Notes for AI coding agents working on beacon. Behavioral spec is [SPEC.md](./SPEC.md) (published to the docs site as `/spec`); user-facing docs are [README.md](./README.md). When the spec and the code disagree, ask — don't silently choose one.

## What beacon is

A Claude Code plugin + sourceable zsh snippet + standalone CLI that surfaces session state two ways: a **terminal-agnostic sessions view** (`wip` / `watch` / `serve`, optionally kept always-on via `beacon serve install`) that reads across all sessions and paints no pane, and an **iTerm2 per-pane render adapter** (a status bar with action buttons, the tab color + two-line label, the window title; the badge is opt-in) for scanning concurrent panes without focusing each. Clicking a session in the dashboard raises its iTerm2 window (serve's `POST /focus` → `beacon-iterm focus`). Both read the same per-session state files — the single source of record; neither inverts that into a daemon. The sessions view works in any terminal; the iTerm2 adapter needs macOS + iTerm2.

## Three deliverables, hard boundaries

| Deliverable | Path | Owns |
|:---|:---|:---|
| **CLI** | `bin/beacon-iterm` | Translating subcommands to iTerm2 control operations — OSC sequences for painted surfaces, Apple Events (`focus` to raise a window, `set-name` to set the window title). **Stateless.** No Claude awareness. |
| **Plugin** | `scripts/beacon`, `hooks/`, `commands/`, `rules/` | Hook handlers, COR resolver for signals, slash command. `rules/` holds ambient rules emitted at SessionStart by `hooks/emit-rules.sh` (e.g. `keep-session-labeled` — proactive task upkeep so the sessions view has signal standalone). Invokes the CLI for every iTerm2 write. |
| **Shell** | `shell/beacon.zsh` | Project name / branch / cwd — refreshed every prompt. Emits its own `SetUserVar` OSC by raw `printf`; calls the CLI for `set-name`. Never goes through the plugin. |

The plugin and shell write to **disjoint user-var slots** so they never overwrite each other. Don't blur this boundary.

The CLI must remain unaware of Claude — it's usable from CI, ad-hoc terminal scripts, or future drivers (e.g., a tmux variant). Don't import plugin state into it.

## Hot paths — keep fast

- `apply()` in `scripts/beacon` — runs on every Claude Code hook. Diff against the resolved-state snapshot before invoking the CLI.
- `_beacon_precmd` in `shell/beacon.zsh` — runs on every prompt redraw, and spawns no process of its own. Last-value sentinels gate every emit; one `git for-each-ref` yields every branch value; the origin URL is memoized per project root; the helpers answer through `_beacon_reply` / `_beacon_binfo` because each `$(...)` is a fork.
- OSC sequences in `shell/beacon.zsh` (profile activation, and every `SetUserVar`) are emitted via raw `printf` **to `/dev/tty`**, bypassing python startup — `_beacon_b64` is a zsh-native base64 so encoding costs no fork either. Writing to stdout instead splices escape bytes into `x=$(cd somedir; …)`, because zsh fires `chpwd` and `precmd` inside command-substitution subshells; the source-time guard refuses to load when `/dev/tty` can't be opened, which only an open attempt detects (`-w` and `-c` both pass on the device node regardless). `_beacon_b64` encodes to UTF-8 first — the branch display carries `↑`/`↓` — and pins `multibyte` / `noksharrays` for its own scope, as `_beacon_branch_info` and `_beacon_precmd` pin the option set their array indexing assumes. The opt-in badge format (BADGE-15) is gated at source, not in the per-prompt hot path, by a value the `shell-init` block carries (CMD-27): one cached, zsh-sourceable block answers the data dir and the badge gate together, and it is regenerated only when the script, the data-dir pointer, or the user config is newer than it — so a new terminal usually spawns no python at all.

## Surfaces beacon paints

Per SPEC.md §4.1 — these and only these:

- **Status bar** — the beacon dynamic profile only (never the user's profile): a fixed strip of `↖ web · project  branch cwd↗`, two action buttons and the branch chip, each edge pairing an action with the data it acts on. `↖ web` resolves at click time via `beacon open-url <cwd>` (STATUS-BAR-08) — no URL handoff file, so it can't drift from the chip (#5). It is *not* redundant with the status-line link (STATUSLINE-02): the footer only exists in a pane running Claude, and the strip is what an ordinary shell has. The branch-review feature (the `⇄ review` chip and the `beacon review` subcommand behind it) was removed wholesale in 2.0 for lack of use. `↗ code` delegates to `beacon open-code` via an absolute interpreter path (STATUS-BAR-07) — an action shell has no interactive `PATH`, so resolving the editor binary there is exactly what would fail. Both buttons read their `label` and `cmd` from `statusbar.buttons.<name>` in the user config (STATUS-BAR-09), and the two halves apply at different times for a reason worth remembering: `cmd` is read on the click, but `label` is baked into the profile (an action component's title can't interpolate a user var), so a label change needs `beacon refresh-iterm-profiles` (CMD-23). The project chip is the project's *name* (STATUS-BAR-02) — no forge identity, no deliverable ref — which is what lets it read the same outside a git repo and outside a Claude session, and what took the per-prompt `resolve-url` off the shell's hot path; the forge identity survives only as the status line's deliverable qualifier (STATUSLINE-03). The branch chip reads by the hybrid model (STATUS-BAR-03): default branch de-emphasized (slate) whatever its state, feature branch by sync state (cyan synced / yellow diverged / orange untracked; green reserved for release). The plugin's `_publish_chips` and the shell's precmd both publish the four hybrid branch slots so Claude-session and interactive panes agree.
- **Tab** — the primary surface, and with the badge off by default usually the only one. With many tabs open only one *pane* is visible, so the strip is the one place a session reaches a user looking elsewhere — and it has exactly two slots for exactly two axes. **Color** (`SetColors=tab=`) carries `activity`: gray / orange / red, three values, one meaning everywhere (BADGE-09). **The glyph on line 1 of the label** carries `mode` (TITLE-06, `MODE_SPECS`). Nothing arbitrates between them, so `release · waiting` is a red tab beside a 🚀 — a state the pre-2.5.0 merged field could not represent at all. Until 2.5.0 a mode owned a hue here too, which spent the always-painted channel on the axis that varies least (~4% of rendered states) and left the 96% axis nothing.
- **Pane background** — a declared mode only, and only by swapping into that mode's profile (RENDER-05), never an ad-hoc background OSC. Outside a mode, the background is the user's profile's. This is the mode's *second* surface and the weaker one: it is visible solely in the focused pane, which is why the glyph and not the background is what carries a mode across tabs. Every mode has a watermark; `retro`'s is drawn by `iterm/marks.py` rather than found art, and `make-bg.py` regenerates all of them through the one slate pipeline so the four read as a family.
- **Window title + tab label** — the session *name* (`TITLE_FORMAT`, two-line: `<b>project</b>` over the indented task via `beacon_task_nl`) surfaces as the two-line tab label and, single-line, as the OS window title showing line 1 (`project`) — so a `/rename`d window keeps its project context in a sea of windows (§4.8, TITLE-05). While a mode is declared, line 1 leads with that mode's glyph (`MODE_SPECS` — `⏸` `🚀` `📋` `🏁`) via `beacon_title_prefix` (TITLE-06). This is the mode's only cross-tab surface, so it is load-bearing rather than decorative; a glyph not the word, since line 1 is shared by the tab and window title (they can't differ), and the mode's free-text note goes to the status line instead. Set via the session *name*, through Apple Events (`set-name`); the profile disables OSC title-setting (`Allow Title Setting: false`) and shows the name via `Title Components: 1`. iTerm2 implements that name as a session-scoped override of the session's copy of the profile `Name` key — the dynamic profile on disk is untouched and `set-profile` still matches, but a beacon pane's `profile name` reads back as the raw template, so iTerm2 diagnostics that quote it (the short-lived-session warning) are unactionable noise (§6.10 caveat 7). It is also why disengagement hands the name back *before* blanking the badge user vars: the other order strands the pane on a template with nothing to interpolate, i.e. a blank tab and window title. The plugin sets it on the first render and re-sets it after each profile swap; iTerm2 re-evaluates the interpolated name as `beacon_project` / `beacon_task_nl` / `beacon_title_prefix` change. The `<b>` accent needs iTerm2's HTML tab titles (recommended by CLI-18); without it the tag renders literally, so it's advisory. Interactive (non-Claude) panes get a `beacon_title` var (project name else abbreviated cwd) the shell writes once at startup, deferring once the pane is Claude-owned (TITLE-04).
- **Badge** — **opt-in, off by default (BADGE-15)**: the tab carries the identity now (color + two-line label), so painting it too is redundant. When enabled (`"badge": "on"` in `~/.config/beacon/config.json`): text (raw project + task, no glyphs — BADGE-11) + the activity color, via OSC. The badge never carries free text (a mode's note lives in the status line, STATUSLINE-01, not here — the badge overlays terminal output, a bad home for a note). The capability is retained in full and gated across all three paint sites: the profile's `Badge Text`, the plugin render, and the shell — which reads the gate from its `shell-init` block (CMD-27).
- **Claude Code status line (STATUSLINE-01/02/03)** — footer rows Claude Code renders from `beacon statusline` (wired into `~/.claude/settings.json` by `install`, which writes that one key and never replaces a `statusLine` the user already set). Terminal-agnostic and non-overlapping (Claude owns the rows), so it's where per-session *values* live. One line per class, empties omitted: the mode's note (led by its glyph) → delivered → open CRs → open issues (epics and milestones ride the issue line); items within a line joined by ` · `. The list is acquired from the **bound tack route** — the deliverables and tracker links of the tacks *this session touched* — plus PROV-07's own resolution, recorded last; `beacon drop <ref>` takes an entry off and keeps it off (CMD-24). The session scope is the part to keep straight: a route's lifetime is the project's, so acquiring the whole route made HOOK-08a's wipe pointless and the row read as a release log of work the session never did. A tack is in scope when it's open (`in_progress` or `pending`) or completed since `session_started_at` — both open statuses, because a route commonly marks its tack done only at ship time and gating on `in_progress` alone emptied the row for whole sessions; PROV-07's resolution is skipped when it only names a route deliverable that shipped earlier (its `_tack_url_for` chain falls back to the newest completed one, which is a fine `↖ web` target but not this session's delivery — so PROV-07 itself is unchanged). Keeping it off the *list* only reaches half the row: the link segment renders the resolution directly when the list is empty, which is every fresh session, so `_publish_chips` substitutes PROV-07's location tiers (`_location_url_at` — open PR for the branch, else branch tree, else project) for a pre-session delivery before persisting `resolved.url`. The substitution is scoped to that state because click-time `↖ web` asks a different question and wants the unsubstituted answer. Each ref is a clickable OSC-8 link, bare (`#4`) for this project and qualified (`otherproj:#75`) for another. Delivered entries (tack `done`/`dropped`, or any `release` kind) render `~ref~ merged 🏁` / `released 🚀` / `closed ✓` in release green and stay on screen. An open CR carries the *badge's own* resolved task as its title (only from the `pr` / `override` tiers) — sourcing it separately is what made the two surfaces disagree. Reads `resolved.*` / `deliverables` from state and **never** calls `resolve_url` — the rows render per prompt and that chain shells to git and possibly `gh`/`glab`.

A mode's **note** is stored with the mode as one value and cleared with it (RES-07): only entering a mode writes either, so a note can't outlive what it annotates. It surfaces in the Claude Code status line (`beacon statusline`, STATUSLINE-01), a footer row Claude owns that never overlaps terminal output, and in the sessions view — plus, while the mode is stood down (`pause` / `done`, STATE-15), on line 2 of the tab in place of the task (TITLE-05a), the note's one cross-tab surface. It stays off line 1, which the window title shares, and off the badge, which overlays output (BADGE-11). General session recall context is `latest_turn`'s job (WIP-11), not the note's: it is derived from the transcript with no agent cooperation and covers most sessions where the note covered a handful.

beacon does **not** paint: terminal fg, tab title, cursor color/shape. Terminal background (color, and a faint image) is the one painted exception, scoped to the mode profile swaps above. The rest belong to Claude Code, the user's profile, or other tools. Adding to this list is a spec change, not an implementation choice. (The **window** title *is* painted, via the session name — see the Window title bullet above and SPEC.md §4.8; the **tab** title remains a non-goal — see §8.)

beacon profiles also explicitly **disable** iTerm2's notification-center delivery (`BM Growl: false`) and terminal-generated alerts (`Send Terminal Generated Alerts: false`). Claude Code triggers these on permission prompts and idle prompts, but beacon already surfaces both via the tab color (and the badge when enabled) — duplicate notifications add no signal.

## Two axes, and they are the contract

Two axes, resolved independently, each owning its own surfaces. No call site arbitrates between them, and none names a hex, a glyph, or an iTerm profile directly:

| Axis | Written by | Maps through | To |
|:---|:---|:---|:---|
| `activity` | hooks only, several times a turn | `ACTIVITY_TO_COLOR_STATE` → `COLOR_PALETTE` | tab (and badge) color |
| `mode` | declared by a user or skill | `MODE_SPECS` | tab / window-title glyph |
| | | `MODE_SPECS` | dynamic profile + pane background + watermark |

The two-step indirection through a logical name (`ready` / `busy` / `blocked`) is deliberate: it's the contract, so the palette retunes in one place. HOOK-03d is not an exception to the independence: nothing consults the mode when mapping an activity to a color, and what a stood-down mode drops is one *observation* — an `idle_prompt` that reports only what the user did themselves — before it is ever recorded. These were **one `status` field until 2.5.0**, merged by a `chain()` that ranked the declared value above the observed one — so a mode discarded the activity beneath it and `release · waiting` could not exist. Don't reintroduce a precedence rule between them; the whole design is that they don't need one.

## State and cache locations

`DATA_DIR` resolves to `$CLAUDE_PLUGIN_DATA` when set (Claude Code provides it for hook invocations). For slash commands, the `~/.local/bin/beacon` wrapper, and the serve service the env var is unset, so the script reads the dir the last hook recorded at `~/.config/beacon/data-dir` — only a hook is told which install is loaded, and Claude Code buckets an inline (local-directory) plugin as `<plugin>-inline` where a marketplace install is `<plugin>-<marketplace>` (e.g. `~/.claude/plugins/data/beacon-chris-peterson/`). Absent a record it derives the same two names from `CLAUDE_PLUGIN_ROOT`. Every invocation context must land on the same dir or hooks write state nothing reads — running beacon inline while the wrapper resolved the marketplace name is what made a live session invisible to `wip`, the dashboard, and the status line.

- Per-session state: `<DATA_DIR>/state/<session-hash>.<field>` — fields include `latest_turn` (most recent conversation turn `{role,text,at}`, auto-derived at hook time and surfaced in the sessions view per WIP-11), `latest_turn_full` (the same turn's full multi-line text, served on demand at `/turn/<hash>` for card expansion per WIP-14), `cc.custom_title` / `cc.agent_color` / `cc.ai_title` (Claude Code's `/rename`, `/color`, and auto-title, harvested from the transcript tail per PROV-09 — the first and third feed the task chain, the color is sessions-view-only), `iterm_session_id` (the iTerm2 GUID focus handle, FOCUS-02), `pending-attention` (sticky attention marker), `override.*` (only `project` / `task` — an override exists where a provider chain sits below it, which is what the prefix means), `mode` (the declared `{name, note}` tuple; absent = `dev`), `activity` (`idle` / `working` / `waiting`, hooks only — no override tier, because a pinned activity outranks the hooks and goes stale), `resolved` (the last-rendered snapshot, which also supplies the identity stability the retired pause-time freeze used to pin into overrides), `resolved.url` / `resolved.url_label` / `resolved.project` (PROV-07's answer — its location tiers when that answer shipped before this session — persisted by `_publish_chips` so the status line never re-resolves; STATUSLINE-02), `deliverables` (the `{ref,url,project}` list the session has touched, sourced from the bound tack route plus PROV-07's resolution, STATUSLINE-03) / `deliverables.dropped` (URLs `beacon drop` took off the row, CMD-24) / `session_started_at` (the window acquisition is scoped to, stamped with HOOK-08a's wipe), `claude_session_id`, `anchor.cwd` / `anchor.project` (SessionStart navigational anchor; Stop re-resolves chips from `anchor.cwd` per HOOK-08/08b).
- Per-session shell handoff files (read by status-bar action buttons): `<DATA_DIR>/cache/cwd-<pane-guid>.txt`, where `<pane-guid>` is the GUID segment of `ITERM_SESSION_ID` (`${ITERM_SESSION_ID##*:}`) — not the full id, whose `wNtNpN` prefix drifts when a pane is moved. Same for the `engaged-<pane-guid>` marker. See `_iterm_cache_key()`. (`url-<pane-guid>.txt` was the URL handoff 2.0 retired; no writer creates one, and `prune` collects the leftovers per WIP-06.) `prune` sweeps these by file mtime — the pane GUID isn't recoverable from a session hash.
- Always-on serve service logs (launchd `StandardOut/ErrorPath`): `<DATA_DIR>/logs/serve.{out,err}.log`

Session hash is SHA-1 (truncated) of the session seed: on iTerm2 the pane **GUID** (the segment of `$ITERM_SESSION_ID` after the last colon) — *not* the full id, whose `wNtNpN` prefix drifts when a pane is moved and would fragment the pane's state into a new bucket on every move; else `claude-session:$CLAUDE_CODE_SESSION_ID` (the id Claude Code sets in every in-session subprocess on any OS, kept whole so a bare `beacon set` on Windows/non-iTerm lands in the same bucket as its hooks), else the tty name, else `default`. See `_session_seed()`. Collisions are not a security concern.

## No iTerm2 prefs written unasked — profile activated at runtime

No hook or render ever runs `defaults write com.googlecode.iterm2 ...`, and beacon is not iTerm2's default profile, so the automatic path sidesteps the plist-cache trap entirely (iTerm2 caches prefs in memory and clobbers any `defaults write` on quit). The one writer is the confirmed, user-invoked `configure --write` below, which handles that trap by writing only while iTerm2 is down. Instead:

- The base `beacon-dev` dynamic profile (the dev cycle) and one mode profile per `MODE_SPECS` entry (`beacon-pause`, `beacon-release`, `beacon-retro`, `beacon-done`) live in `DynamicProfiles/`; iTerm2 watches the directory and reloads them live, so the profile step needs no iTerm2 restart. Each mode profile is derived from the base at install time (same layout, distinct background — pause gets a faint `||`-button background image, release a faint rocket one, retro a faint checklist-clipboard one, done a faint checkered finish-flag one) so they never drift.
- Each session is switched *into* the base `beacon-dev` profile at runtime via `set-profile` (OSC `SetProfile=`): the plugin at SessionStart, the shell snippet on source. Badge/tab color then layer on via OSC `SetColors=`. The per-state profiles are the **mode profiles** — a mode state (`paused`, `release`, `retro`, `done`) swaps into its profile for the background change a color OSC can't express (RENDER-05); ready/busy/blocked (dev) stay OSC overlays on the base. The logical-mode → profile mapping lives in `MODE_SPECS`, so call sites never name iTerm profiles.
- Every *beacon-owned* install step lands in place. The **one** path that writes an iTerm2 preference is `configure --write` (CLI-18, fronted as `beacon layout` per CMD-28) — confirmed per setting and again before the quit — which applies the app-wide layout prefs (tab position/size, status-bar position) that no dynamic profile can carry. It resurrects the quit-write-relaunch orchestration (once `exclusive-configuration`): confirm the restart, spawn a detached helper that waits for iTerm2 to exit, write, and relaunch. `install` closes by running it, so the recommended layout is actually applied rather than described — left advisory it stayed drifted, since the closing line read as nothing left to do. Whether iTerm2 is running is decided by asking it through Apple Events, never `pgrep -x iTerm2`, which never matches the running app (macOS matches `-x` against the full executable path) and so sends the write into a live iTerm2 that restores the old values on quit. Never call it from a hook or render — it closes every window and pane.

## Session focus (FOCUS)

Clicking a session in the dashboard raises its iTerm2 window. The chain: dashboard `POST /focus {hash}` → `serve` resolves `hash` → the recorded `iterm_session_id` GUID **server-side** (the GUID never reaches the browser) → `beacon-iterm focus <guid>`. The CLI's osascript **captures the target with no side effects, then** selects session→tab→window→activate — selecting mid-enumeration reorders iTerm2's window list and throws `Invalid index -1719` on nested splits. The `/focus` route is loopback-only with a Host-header rebind check and an Origin allowlist (FOCUS-04); `GET /wip.json` keeps its permissive CORS. Non-iTerm sessions record no handle and are not focusable (`focusable: false` in the payload).

## Conventions

- **No fallbacks.** Don't add a "simple alternative" path inside a try/except around the real logic. Let primary failures surface. (`_cli()` is an exception — it deliberately swallows errors so a bad CLI invocation can't crash a hook.)
- **No comments explaining WHAT.** Good identifiers do that. Comments capture WHY: hidden constraints, subtle invariants, workarounds. Re-read existing code comments before adding new ones — most explain non-obvious WHYs and should be kept.
- **No backwards-compat hacks.** Rename, delete, restructure freely.
- **No symlinks.** If you think you need one, stop and ask.
- **Imperative commit subjects, ≤50 chars** ([cbea.ms style](https://cbea.ms/git-commit/)).

## Running things

| Task | Command |
|:---|:---|
| Run plugin once | `python3 scripts/beacon <subcommand>` |
| Bootstrap install | `python3 scripts/beacon install` |
| Focus an iTerm2 session window by its id | `python3 bin/beacon-iterm focus <session-id>` |
| List active work streams across all sessions (last 24h) | `python3 scripts/beacon wip [--json] [--since 1d] [--all]` |
| Serve the bundled dashboard (`/`) + wip snapshot (`/wip.json`) | `python3 scripts/beacon serve [--port 8787]` |
| Manage the always-on serve service (launchd/systemd) | `python3 scripts/beacon serve <install\|uninstall\|status>` |
| GC per-session state + per-pane cache files for long-idle panes | `python3 scripts/beacon prune [--since 30d]` |
| Delete per-session state for one session | `python3 scripts/beacon forget <hash>` |
| Render the Claude Code status-line row (mode note + deliverable links) | `echo '{}' \| python3 scripts/beacon statusline` |
| Reload shell integration | `exec zsh` |
| Smoke test the CLI | `python3 bin/beacon-iterm <subcommand>` (writes OSC to `/dev/tty`) |
| Regenerate the mode watermarks after editing `iterm/marks.py` | `python3 iterm/make-bg.py [<mode>...]` |
| Run unit tests | `just test` (loads `scripts/beacon` via importlib, mocks `_cli`) |

The test suite under `tests/` covers plugin-side behavior (apply/render emit decisions, override propagation, focus handle + `/focus` route). Surface verification (the actual badge / status bar / tab color rendering, and the focus action, in iTerm2) still requires sourcing the shell snippet and looking.
